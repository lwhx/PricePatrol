# 采集与预警分离

## 用户要求

采集任务和监控预警任务独立配置。调度器按计划创建采集作业；只有定时来源的采集作业完成后，才自动执行关联预警。手动采集只更新价格，不执行预警、不发送自动汇总。

## 实现选择

保留 Node 24、Fastify、SQLite 和 Vue，新增独立预警任务及预警执行表。一个采集任务可以关联多个预警任务，共用一次采集的冻结价格证据。只在原组合任务上加一个通知开关无法满足独立预警配置；引入外部消息队列对当前单实例应用没有必要。

以下边界由实现方选定：

- 定时作业的 success / partial 终态触发评估；partial 只使用本批数据，明确覆盖不完整。failed、stopped、auth_required、recoverable 不触发。
- 点击立即运行、店铺采集、批量重采、失败项重试均创建 manual 作业。恢复同一作业保留创建时的来源。
- manual 与 scheduled 去重分别处理，计划到期不会把手动作业升级成定时作业，也不会复用手动批次作为预警证据。
- 预警规则、范围、白名单和通知开关在定时采集入队时冻结。修改影响之后创建的定时批次。
- 预警任务可暂停或删除；已经捕获的执行快照保留。停用/删除采集任务清除其尚未开始的定时作业。
- 预警检查与通知使用独立队列。通知失败不改变采集报告，也不重采商品。
- 每个采集批次与预警任务最多创建一个预警执行；重启补齐尚未派发或未结束的预警，不重评已完成记录。

## 数据与接口

- CollectionTask：沿用 tasks 表及 /api/tasks。保存店铺、采集范围、计划、启用状态和版本。
- AlertTask：新增 alert_tasks 表及 /api/alert-tasks。保存 collectionTaskId、shopId、范围、规则、白名单、通知、启用状态和版本。
- Run：仍是采集执行；增加 trigger: manual | scheduled | legacy、alertDispatchStatus。其内部快照包含采集配置和关联预警任务配置。
- AlertRun：新增 alert_runs 表，独立保存 collectionRunId、alertTaskId、状态、检查/排除/命中/未知数量、规则快照及通知状态。
- Alert：保留 runId 指向采集证据，增加 alertRunId。唯一键包含预警执行，允许多个规则任务检查相同 SKU。
- /api/alert-runs：查询预警执行。/api/alert-runs/:id/notify：仅重试对应预警汇总。
- 价格查询的 taskId、白名单批量操作改为预警任务上下文；添加采集范围仍操作采集任务。

## 升级迁移

事务内将旧组合任务拆为原 ID 的采集任务和同 ID 的默认预警任务。保存原范围、计划、规则、白名单、通知开关；不合并不同旧任务。历史采集、价格和预警保留。旧执行没有可信来源，一律标记 legacy，不因升级补发历史预警。迁移可重复打开且不复制任务，失败应回滚。

## 界面

分别提供采集任务与预警任务列表、编辑页和执行记录。采集页只设置商品与计划；预警页绑定采集任务，设置规则和白名单。采集记录展示手动/定时/旧版本来源，预警记录展示来源批次及覆盖情况。手动按钮明确说明只采集。

## 验收

1. 同一个有每日计划的任务，点击立即采集仍不预警；真正调度触发才预警。
2. 手动和定时作业同时排队不串用来源。
3. 一次定时采集可独立触发多个预警任务，分别保存白名单、规则版本及事件。
4. 手动失败重试不触发；定时作业停止后恢复只在最终完成时触发一次。
5. 部分完成标明覆盖不足；旧价和缺价不得用于认定价格正常。
6. 重启补派发、重复回调、通知重试不重复评估或重采。
7. 旧数据库升级保留数据且不发送历史预警；跨店错误关联被拒绝。

本次围绕分离任务实现，顺带修复妨碍该流程的恢复写价、队列截断和凭据竞争问题。其他此前审查的问题不视为本次已修复。
