# 可靠性与运行维护优化实施记录

本轮按“采集和数据正确性 → 长期运行维护 → 预警生命周期和性能 → 验证发布”的顺序实施。设计与逐项计划分别见 [规格](superpowers/specs/2026-11-22-reliability-operations.md) 和 [实施计划](superpowers/plans/2026-11-22-reliability-operations.md)。

## 保持的业务边界

- 只有调度器创建且最终成功或部分完成的定时采集，才触发入队时冻结的关联预警任务。手动采集和失败商品手动重试不触发预警。
- 历史采集、规则快照、检查证据和通知候选保持不可变；人工处理状态属于独立的异常事项。
- 使用现有单服务、SQLite 和 Node.js 24 部署，不增加消息队列或数据库服务。两份部署配置均发布 `6300:3000`，不限定宿主机回环地址。

## 一、采集和数据正确性

采集器区分需要重新登录与限流、网络和超时等暂时失败。账号校验、Cookie 导入和网页登录回调使用凭据版本检查，避免旧请求覆盖新登录状态。网络重试、身份探测和限流等待都有上限；不跟随未经检查的重定向。

只有经身份和 SKU 覆盖核验的完整商品结果可以移除当前列表中已消失的 SKU；部分结果保留原数据。暂停批次在其他采集完成后恢复时，重新协调未完成商品的批次快照。已经结束的报告保持原样。金额解析保留接口原始数值文本，避免较大金额先经过 JavaScript 浮点数而失去分位精度。

批量采集按店铺记录成功与失败，重试只提交失败分组。服务端保存 24 小时的请求幂等凭据，HTTP 响应丢失后再次提交仍返回原批次。向采集任务添加商品使用原子追加，整份配置编辑使用版本冲突检查。商品汇总导出保留汇总字段，日期筛选恢复时正确转换本地时间与 UTC。

## 二、长期运行维护

| 配置 | 默认值 | 说明 |
| --- | --- | --- |
| 普通历史保留 | 180 天 | 清理时仍保护当前价格来源和未完成工作 |
| 预警证据保留 | 365 天 | 未解决事项和仍需投递的证据受保护 |
| 自动清理 | 关闭 | 升级不会自动删除历史，设置页可预览后开启 |
| 自动备份 | 开启，每 24 小时 | 使用一致性 SQLite 快照并检查完整性 |
| 本地备份份数 | 14 份 | 只轮换应用自己生成且已完成的备份 |
| 备份目录 | `/app/backups` | Compose 使用独立 `pricepatrol-backups` 卷 |

手动和自动清理都先成功备份，再按同一套预览规则删除。未完成重试所依赖的父采集、未过期幂等凭据、待处理预警、当前价格及活动异常的关键证据不会被误删。备份或配置的远端副本失败时不继续清理。

运行健康页面显示最近成功采集、数据时间、连续失败、队列和计划跳过原因；维护页面显示备份及清理状态。日志包含请求、采集和预警执行标识，不记录 Cookie、通知密钥、请求正文或不受控的远端错误详情。镜像包含构建提交、时间及数据库结构版本。

首次生产初始化需要管理员预置密码或部署者持有的初始化令牌；已有管理员继续使用原密码。自动生成的令牌仅保存在权限受限的文件中，不由公开状态接口返回。

## 三、预警生命周期和性能

同一预警规则下的同一 SKU 持续异常共用一个处理事项，区分首次出现、持续、恶化和恢复。人工确认、备注和处理完成与实际价格恢复分开。规则语义改变会归档原事项，改名或调整通知设置不会重新开启。缺价、旧价、采集失败和白名单排除不能证明恢复。

持续异常默认每 24 小时可以提醒；首次和符合数值方向的恶化可以立即提醒。恢复通知默认关闭。候选在检查事务内冻结，通知重试复用这份候选。全局通知关闭或密钥未配置且确定没有发送时，不消耗提醒冷却；已接受、正在发送或结果未知的失败仍保留预留，防止自动重复投递。

观察顺序按价格实际采集时间判断，并保存不依赖历史源记录存活的稳定顺序。因此，旧批次恢复后采到的新价格能够参与判断；已经采到的旧行不会覆盖更新的状态。历史清理保留仍有效的冷却信息。

| 性能设置 | 默认行为 |
| --- | --- |
| 查询计算 | 合并重复筛选与统计，保持精确金额排序和未知值语义 |
| 小结果复制 | 保留预览及复制接口 |
| 自动文件导出阈值 | 超过 2000 个源行或 5 MiB |
| 后台导出执行 | 一个工作线程活动任务，排队和运行合计最多 20 个 |
| 导出文件保留 | 24 小时 |
| 小复制快照保留 | 15 分钟，最多 32 份 |
| 跨店采集并发 | 默认 1，可通过 `COLLECTION_CONCURRENCY` 设为 1–4；同店始终串行 |

大导出在独立只读连接的一致性读事务中分批写文件，通过认证接口流式下载，网页不接收完整大文件正文。取消、进程重启、文件缺失、磁盘和 SQLite 写入失败都有可查询的结果；关闭服务前结束等待中的导出请求。导出和备份线程不继承父进程的凭据环境变量。

## 验证与发布记录

定向回归覆盖采集身份和金额、账号竞争、部分结果、批量幂等、保留策略、备份恢复、异常生命周期、通知冻结、导出格式一致性、并发和界面交互。独立审查发现的问题已进入对应修复与复审，不将测试夹具结果表述为真实商家采集验收。

本地对最终修复提交 `6339427` 执行 `npm run check` 成功：服务端 45 个测试文件、335 项通过，界面 14 个测试文件、70 项通过，服务端和 Vue 类型检查、生产前端构建均通过。1 项可选真实浏览器测试因本地缺少 Chromium 跳过，CI 会显式启用并安装所需浏览器。前端构建仍提示现有大型依赖分包超过 500 kB，但构建成功；本轮未以调整警告阈值掩盖体积。

整分支审查补查出五处跨模块问题，随后在同一轮修复并验证：

| 场景 | 修复后的行为与证据 |
| --- | --- |
| 暂停后商品消失 | 保留停止前的价格证据，同时保留采集器报告的失败商品；实际采集和预警 worker 回归确认异常继续活动，恢复候选为零 |
| 定时采集时凭据过期或身份变化 | 采集与账号验证共用失效分类，暂停原批次；下一次计划跳过失效账号，更换凭据后可恢复原批次 |
| 大量历史记录清理预览 | 受保护父任务集合只计算一次，并为当前价格及预警证据的采集 ID 建索引；升级数据库的实际查询计划和预览/删除一致性通过验证 |
| 备份本地或副本写入中断 | 下一次写入前回收严格匹配当前实例的中间文件；实际子进程退出及跨进程争用测试确认活动文件、无关文件和历史数据受保护 |
| 全局通知关闭后重新开启 | 有冻结候选的执行可在界面上重试，提交原预警执行 ID；任务关闭通知、空候选、已接受或正在发送的记录保持不可重试 |

性能对比使用同一台机器上的无价格、无预警、无重试历史夹具：1,000 / 2,000 / 4,000 条采集记录的预览分别从 104 / 407 / 1,701 毫秒降至 2 / 4 / 7 毫秒。这是单次本地测量；自动化测试断言查询计划和结果语义，不把毫秒数当作生产性能承诺或易波动的通过门槛。

最终修复已通过独立范围复审：五项问题均确认已解决，未发现修复引入的新问题。发布结果由 [PR #2](https://github.com/lwhx/PricePatrol/pull/2) 和其关联 GitHub Actions 记录。PR 验证包含真实 Chromium 和 Compose 配置；主分支发布先分别验证 AMD64、ARM64 镜像，再合并镜像清单。实际部署到用户服务器需由服务器更新镜像完成。

## 部署者需要保留或配置的内容

- 升级前备份现有数据，保留原 `ENCRYPTION_KEY` 和原数据卷名称。数据库与密钥必须配套恢复。
- 本地备份卷无法应对整机丢失。异机副本需要宿主机先挂载支持 SQLite 文件锁的远端存储，再配置 `BACKUP_COPY_DIR`；详细配置和恢复步骤见 [README](../README.md#备份与恢复)。
- 自动清理默认关闭。先检查清理预览和备份结果，再按所需保留周期开启。
- 使用镜像的构建提交标签可以固定版本；升级后的结构不应直接交给旧镜像读取，回退应恢复升级前备份。

## 实施决策

用户已授权执行全部优化并合并推送，因此完成验证后直接进入发布。同一阶段内对互不冲突的模块并行实现，按阶段顺序集成；每个跨模块接口由统一集成检查覆盖。错误判断接口边界会造成集成回归，因此对保留策略、预警冻结、鉴权和导出关闭顺序安排了独立复审。

本地缺少容器引擎与真实 Chromium 的检查交由 GitHub Actions 执行；源码测试、类型检查、UI 测试和前端构建在本地执行。如果 CI 的真实运行结果失败，就暂停合并或镜像清单发布并修复，不以本地夹具通过替代。没有使用真实商家账号、发送外部测试通知或操作生产服务器。

草稿 PR 的 CI 与最终只读复审并行，合并仍以两项检查均通过为前提。这样可以提前发现真实浏览器和 Compose 环境问题；代价是复审修改源码后需要重跑 CI。最终复审确认的五项问题已统一修复，再以更新后的分支重新执行发布门槛。
