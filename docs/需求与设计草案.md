# 电商价格监控：需求与设计草案

状态：早期需求记录。当前完整功能方案以同目录的 [功能方案.md](功能方案.md) 为准；发生冲突时采用新版方案。产品代码尚未实现。项目根目录：`F:\Hermes\项目\电商价格监控`。部署目标：Linux 服务器 Docker。外部通知渠道按用户要求最后实现。

## 已明确的目标

- 独立 Web 程序，支持多个账号，一个账号绑定一家淘宝或天猫店铺。
- 支持导入 Cookie；也支持用户登录服务端浏览器中的商家后台，程序取得该次登录会话。
- 采集商品 ID、标题、独立 SKU ID、完整规格、SKU 后台标价、页面优惠前价格、页面优惠后价格。
- 优惠后价格以详情页实际展示的字段为准。
- 采集数据写入数据库，页面查询数据库中的结果，支持排序、筛选、查找等操作。
- 用户创建监控任务，采集结束并完成对应结果入库后，按任务条件检查折扣并报警。
- 支持任务白名单：按商品 ID 精确排除；按商品标题包含的关键词排除。例如标题包含“自由岛”的商品不参加该任务的折扣预警。

## 当前取数证据及边界

本机当前天猫会话的纯 HTTP 已通过真实请求验证：商品列表两页40个不重复商品；后台首页20个商品789个SKU；3个商品34个SKU的后台标价、详情优惠前、详情优惠后均匹配。服务端补发 MTOP 签名令牌后，HTTP客户端重新签名重试成功。

浏览器仅在开始时提供当前 Cookie；取数由 Python requests 独立完成，解析复用现有 JavaScript 模块。此结果不等于淘宝账号、Linux服务器出口、多账号隔离、长期任务和网页登录已通过验收。登录失效后重新登录与MTOP签名令牌补取是两种能力。

## 建议技术选型（尚非用户指定）

- 后端：Node.js 24 LTS、TypeScript、Fastify。提取已有 JavaScript 价格解析、平台适配与匹配模块。
- 前端：Vue 3、Element Plus、AG Grid Community。
- 数据：SQLite、Drizzle，金额保存为整数分，商品ID/SKU ID保存为字符串；数据库使用Docker持久数据卷。
- 传输：纯HTTP客户端、每账号独立Cookie容器与MTOP签名逻辑。
- 登录辅助：独立Playwright/Chromium服务，提供受控网页操作入口，仅登录或人工验证时使用浏览器会话。
- 初版单实例部署与单一任务调度所有者；数据库记录执行状态和进度，不引入Redis作为初版前置依赖。

## 数据流与页面行为

1. 账号登录/导入后核验实际店铺归属、平台与商品读取权限。
2. 执行任务时固定店铺、采集范围、规则版本和白名单快照，避免执行中编辑规则影响同一次判断。
3. 通过后台分页读取商品及SKU标价，再读取对应商品详情价格，按店铺＋商品ID＋SKU ID严格匹配。
4. 将有效结果、缺失原因、任务进度、来源和时间写入数据库。采集中的数据明确标为进行中。
5. 结束时确认结果入库，再评估本次新获取的有效价格，保存预警记录并触发通知。
6. 页面通过后端接口查询数据库，不因排序、搜索、筛选或打开详情重新请求淘宝/天猫。

最新结果与历史快照分开保存。某个SKU本次失败时，界面可展示上次成功价格及其原时间，但本次状态必须标失败/陈旧，不得作为本次新价格参加折扣判断。

价格表支持店铺、商品ID、标题关键词、SKU规格、价格区间、折扣区间、采集状态、预警状态与采集时间筛选；支持金额/折扣/时间排序、分页、查看历史及导出。建议支持从选中商品批量加入某个任务白名单。这些筛选与排序应由后端数据库查询完成，不能只处理当前已加载的一页。

当前“数据操作”按查看、排序、筛选、查找、导出、任务规则和白名单管理理解；不推定用户授权程序修改商家商品价格。

## 监控任务

建议任务包含以下配置：

| 项目 | 行为 |
| --- | --- |
| 名称 | 便于区分店铺和策略 |
| 店铺 | 初版每个任务绑定一家店，可为不同店建立多个任务 |
| 范围 | 全店在售商品或指定商品ID |
| 执行方式 | 手动、每天定时；定时采用Asia/Shanghai并在界面显示 |
| 规则 | 首版重点为“实际折扣严格低于指定阈值” |
| 白名单 | 商品ID列表、标题包含关键词列表 |
| 通知 | 渠道与启用状态，具体渠道待确定 |
| 运行记录 | 进度、成功/失败数量、命中/排除/无法判断数量与通知状态 |

同一家店同一时间只运行一个采集作业；不同任务并存时排队执行，任务之间不覆盖规则。全局限制请求并发，固定池完成一个补一个，最大值不超过现有约定5。具体默认频率留给实现者根据真实接口响应设定。

## 折扣规则

实际折扣 = 页面优惠后价 ÷ 后台SKU标价 × 10。

- “低于8.5折”指严格小于8.5，等于8.5不报警。
- 计算使用整数分交叉相乘；显示值的四舍五入不参与规则判断。
- 后台标价为0、身份/来源不匹配、本次优惠后价缺失或任一参与价格已陈旧时标为“无法判断”，单独列出原因。
- 详情优惠前是独立对照列，不替代后台标价作为折扣分母。
- 按SKU评估。某商品任意一个未排除的SKU命中即将商品计入预警商品数，同时保留具体SKU明细。

可扩展条件示例（尚未逐项确认为首版范围）：优惠后价低于指定金额、后台标价与详情优惠前价不一致、折扣或价格相较上一次变化超过阈值。规则结构应可扩展，但不为未确认条件承诺已实现。

## 白名单

建议白名单归属于具体任务，可启用、停用、编辑、删除并填写备注。

- 商品ID：精确匹配。该商品的所有SKU均不参与此任务预警。
- 标题关键词：商品当前标题包含该文本即排除。例如“自由岛”匹配“自由岛沙发”“双面沙发自由岛横厅可坐”。
- 多条白名单采用“任意一条命中即可排除”；商品ID和关键词之间同样为或关系。
- 关键词首版按普通文本包含匹配，去掉输入首尾空白、拒绝空词，不默默使用正则表达式或分词。
- 排除只影响预警，商品及SKU仍采集入库，可在数据页查找历史价格。
- 在任务结果中展示排除数量及原因，例如“商品ID白名单”“标题包含：自由岛”。
- 规则修改仅影响后续执行；历史预警保留当时的规则与排除依据。

判断示例：

| 商品/情况 | 折扣 | 白名单 | 结果 |
| --- | --- | --- | --- |
| 普通沙发 | 8.2折 | 未命中 | 报警 |
| 指定特价商品 | 7折 | 商品ID命中 | 排除，不报警 |
| 自由岛双面沙发 | 8折 | 标题包含“自由岛” | 排除，不报警 |
| 普通沙发 | 8.5折 | 未命中 | 不报警 |
| 某SKU本次优惠后缺失 | 未知 | 未命中 | 无法判断，不能报正常 |

## 任务结束、异常与通知

- 状态区分排队、运行、成功、部分完成、失败、停止、等待登录/验证。
- 全量成功时检查全部有效记录；部分完成时仍检查已经获取并入库的本次有效记录，通知中标明未检查数量与采集异常，不能声称全店正常。
- 无有效价格可检查时报告采集异常，不发送“未发现异常价格”的正常结论。
- 用户手动停止时保留进度和结果，不触发正常的完成通知；继续作业后再执行完成评估。
- 同一次执行的预警评估和通知需要幂等键，避免重试重复发送。初版建议每次任务执行生成一份汇总，而非每个SKU各发一条。
- 汇总包含店铺、任务、时间、折扣阈值、检查/排除/异常数量和命中SKU明细，数据页可追溯该次执行。
- 是否跨天只提醒新增异常、或每天重复提醒仍异常的商品，尚待确定；当前建议每次完成都生成报告，同次执行不重复发送。
- 业务预警先入库，通知失败单独重试并保留失败状态，不重跑采集。
- Cookie与授权数据加密保存，管理界面需要登录；日志与导出不包含Cookie、签名和完整请求头。

## 建议的数据实体

账号/店铺、商品、SKU、采集作业、每次价格快照、监控任务、规则版本、任务白名单、预警事件、通知投递记录。

任务/商品/SKU记录均绑定店铺身份。商品与SKU变化需根据成功完整采集的覆盖范围判断，失败或部分采集不能直接推断商品已下架。
